# ТМ · 04 — Flutter: каркас и автосборка APK. План и решения

Подготовлено: 08.11.2026 (Екб), чат ТМ · 03. Копия — документ проекта «ТМ · 04 — план Flutter и принятые доработки».

## Цель ТМ · 04 (этап 1)
Тестовый APK на Flutter, который собирается автоматически в GitHub Actions и умеет:
1. Импорт пакетов конвертера: один или несколько ZIP формата qs-manual-pack v1 (`index.json`, `search.json`, `techdata.json`, `proc/*.html`, `img/*`), с прогрессом «Пакет k из N».
2. Дерево «машина → агрегат → процедуры» и просмотр процедуры: HTML с картинками, без сети.
3. Поиск по процедурам на SQLite FTS5. `search.json` используется только при импорте для наполнения индекса.
4. Русский интерфейс, крупные элементы под перчатки, светлая и тёмная тема.

Остальные доработки из списка ниже на этапе 1 не делать, но схему БД заложить так, чтобы их не пришлось переделывать.

## Технические решения
- Flutter (stable), Riverpod 3, Drift (SQLite с FTS5), go_router. Структура — по скилам flutter:* (сначала читать flutter:flutter-conventions-index).
- Пакет Android: `ru.technomining.engineer`, версия 0.4.x-test.
- Облачная среда Claude не скачивает Flutter SDK. Поэтому код пишется без локального запуска, а проверку делает GitHub Actions: `flutter analyze`, `flutter test`, `flutter build apk`.
- Платформенные папки (`android/`) workflow создаёт сам: `flutter create --platforms android --org ru.technomining --project-name engineer .` при отсутствии папки. Можно один раз сгенерировать их в Actions и закоммитить.
- APK подписывается отладочным ключом (тестовая сборка). Результат — Artifact запуска, `engineer-0.4.x-test.apk` и SHA-256.
- Workflow `build-apk.yml`: запуск по пушу в `main` (пути `app/**`) и вручную.
- Код приложения лежит в `app/`, конвертер — в `converter/`.

## Принятые доработки (решение пользователя 08.11.2026)
1. **Поиск на SQLite FTS5** вместо `search.json`. Учитывать русские окончания (нормализация и поиск по префиксу), не держать индекс в памяти. *Этап 1.*
2. **Обновлять только изменённые процедуры.** Хеш у каждой процедуры и картинки в `index.json`; при обновлении пакета докачивается только разница. Нужна доработка конвертера (поле `sha`) и сервера. *Схема БД — в этапе 1, докачка — позже.*
3. **Подсветка замера при вводе:** зелёный — в допуске, жёлтый — у предела, красный — вне допуска. Цвет всегда дублируется значком и текстом (✓ / ! / ✕).
4. **Голосовой ввод без интернета** для замечаний (распознавание речи на устройстве, русский язык).
5. **Фото с пометками:** обвести, стрелка, подпись на снимке. Снимок привязан к узлу и замеру. Оригинал хранится отдельно.
6. **Шаблоны отчётов по типу работ:** полная разборка, частичная разборка, выезд. Набор узлов и замеров задаётся шаблоном.
7. **Очередь отправки (outbox):** всё сохраняется на устройстве, на сервер уходит при появлении связи. Фото и видео по умолчанию только по Wi-Fi и в сжатом виде; в настройках можно разрешить мобильную сеть.
8. **Совместное редактирование отчёта без сети** — схема ниже.
9. **Журнал сбоев на устройстве:** ошибки пишутся в локальный журнал и отправляются при синхронизации. Сторонних сервисов аналитики нет.
10. **Очередь главного инженера:** допуски на утверждение, «как ещё говорят», отчёты на проверке — на одном экране, с уведомлениями.

## Совместное редактирование отчёта без сети
Задача: несколько инженеров правят один отчёт, в том числе без связи. Ничего не должно теряться. Приоритет — у изменений автора отчёта (предложение пользователя).

**Принцип: отчёт — набор мелких записей, а не один документ.**
- Узел, замер, фото, замечание, отметка «осмотрен» — отдельные записи со своим id (UUID), автором и меткой времени. Метка — гибридные часы (HLC), чтобы порядок не зависел от неверного времени на телефоне.
- Каждое изменение сохраняется как операция в журнале: кто, что, когда, старое и новое значение. На сервер отправляются операции, а не отчёт целиком.

**Правила слияния:**
| Ситуация | Что происходит |
|---|---|
| Разные инженеры правят разные записи (разные узлы или замеры) | Сливается автоматически, конфликта нет. Это основной случай: инженеры обычно работают по разным агрегатам. |
| Новые фото, замечания, замеры | Только добавляются, конфликтов не бывает. |
| Два инженера изменили одно поле одной записи | Побеждает значение **автора отчёта**. Если автор это поле не трогал, побеждает более позднее изменение. Проигравшее значение не удаляется: оно сохраняется как «другое значение» и показывается в списке «Расхождения». |
| Повторный замер одного параметра | Каждый замер — новая запись (кто, когда, значение). В отчёт идёт последний замер автора или назначенного им инженера, остальные остаются в истории замеров. |
| Один удалил, другой изменил | Изменение сохраняется, удаление помечается как спорное и попадает в «Расхождения». Удаление всегда мягкое: запись скрывается, но остаётся в базе. |
| Отчёт отправлен «на проверку» или утверждён | Прямые правки закрыты. Правки других инженеров, сделанные без сети до блокировки, становятся предложениями: их принимает автор или главный инженер. |

**«Расхождения»** — список в отчёте: поле, оба значения, кто и когда. Автор выбирает одно значение одним нажатием. Пока в отчёте есть нерешённые расхождения, отправить его на проверку нельзя.

**Кто может править:** автор и инженеры, которых он добавил в отчёт. Главный инженер может править всегда.

На этапе 1 реализуется только схема БД (id, автор, HLC, мягкое удаление, журнал операций). Слияние — на этапе синхронизации.

## Правила для запуска без пользователя
- Сначала проверить лимит: встроенный браузер → https://claude.ai/settings/usage. Если использовано ≥ 90% или уже тратятся кредиты, выполнить «передачу» (точка возврата + STATE.md) и остановиться.
- Не менять требования и концепцию. Решения, принятые в ходе работы, записать в «Точку возврата» как «решено без пользователя — проверить».
- Не трогать `converter/` и релиз `pdf-library`.
- Готово, когда в Actions есть успешная сборка APK. Обновить «Тестовое приложение Android» (версия, SHA-256, что изменилось), STATE.md и «Точку возврата».
